# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

This project builds on [sunsynk-api-client](https://pypi.org/project/sunsynk-api-client/) by James Ridgway (installed via pip) and adds energy cost analysis and battery simulation tools.

## Setup

```bash
bash setup.sh          # creates venv and installs requirements
```

Credentials are passed via environment variables:
```bash
export SUNSYNK_USERNAME=...
export SUNSYNK_PASSWORD=...
```

## Architecture

### `sunsynk/` — upstream API client library (PyPI dependency)

Installed via `pip install sunsynk-api-client`. A thin async wrapper around the Sunsynk REST API (`https://api.sunsynk.net`). Authentication uses RSA+MD5.

- `SunsynkClient` — async context manager. Use `async with SunsynkClient(u, p) as client:` or `await SunsynkClient.create(u, p)`.
- API data models: `Battery`, `Grid`, `Input`, `Output`, `Inverter`, `Plant`, `Vip` — all extend `Resource`

### `analysis/` — our extensions and energy analysis engine

- `collectdata.py` — standalone CLI script; iterates over all historical months/days and prints a financial analysis of the solar/battery installation. Can be run from any directory (`python analysis/collectdata.py ...` or `python3 collectdata.py ...` from within `analysis/`). It sets `PROJECT_ROOT` from `__file__` and calls `os.chdir(PROJECT_ROOT)` at startup so imports and `inverterData/` paths always resolve correctly. Settings are loaded from `config.json` (project root) then overridden by any `key:value` CLI args; use `config:path.json` to load a different file. Battery-related settings (`batterySize`, `usePV`, `startCharge`, `stopCharge`, `exportWindowStart`, `exportWindowStop`, `useExport`, efficiencies) all live under the `virtualBattery` key in config. The month/day iteration itself lives in `_iter_energy_days()`, an async generator shared with `graphs.py`: it fetches/caches `EnergyMonth`/raw day JSON, builds/reuses `EnergyDay`, calls `prices.check_date()`/`energyday.run_battery()`/`prices.add_data()`, and yields `(date_str, energyday, battery_delta)` per day — `battery_delta` is that single day's change in the battery's cumulative counters, snapshotted immediately around `run_battery()` because `EnergyPrices._make_battery()` swaps in a fresh `VirtualBattery` (counters reset to 0) whenever a tariff period rolls over, so a delta can never be computed by diffing across days.
- `graphs.py` — standalone CLI script generating an interactive HTML dashboard (Plotly, self-contained/offline-capable) instead of the text report: daily spend (with rolling-average overlay), net daily cost (spend minus export income), ROI (£ and %) with a rate-of-change chart for each (each day's own contribution to cumulative ROI, not a finite difference), payback curve (cumulative investment vs savings), daily energy flows (PV/Load/Export/Import), daily battery charge/discharge, and one 5-minute-interval PV/Load/Export/Import chart per day for the top/bottom 5 ROI days and top 5 spend days (ranked by each day's own contribution to cumulative ROI, `savings_inc_seg`, or by `spend`) — the actual within-day shape, read straight from `EnergyDay.pv`/`.load`/`.grid`'s raw records (`_interval_time_series`, `_grid_import_export_series`, `_fig_day_interval_detail`), not the daily kWh totals. `main()` retains each processed date's `EnergyDay` in `energyday_by_date` for this (ranking only happens after the full date range is processed, so which ~15 days end up needed isn't known until the end). `_select_extreme_days` caps selection to one day per calendar month (`_pick_unique_months`) so a single unusually good/bad/expensive month can't take every slot; each selected day carries its TRUE position in the full ranking (not its position in the deduplicated list), so a chart titled e.g. "#7" still means the 7th-ranked day overall even though ranks 3-6 were skipped as same-month duplicates. The day-ranking (`_select_extreme_days`) and per-day figure assembly (`_interval_detail_figures`) are shared by the ROI-days and spend-days charts — only the ranking key differs. Reuses `collectdata.py`'s `_load_settings`/`_make_battery`/`_iter_energy_days` and scopes to the primary scenario (first `energyPrices` file, first `virtualBattery` config, baseline `pvBoost`). Per-day figures are computed by `dailyseries.py`'s `DailySeriesBuilder`, not `EnergySummary` (which only retains running totals per tariff period, never a day-by-day series). Output goes to `results/_{timestamp}{-desc}-graphs.html` by default (or `outputPath` override); `rollingWindow` and `plotlyCdn` (embed vs CDN plotly.js) are graphs.py-specific config keys. The energy-flows chart also overlays a dashed **"Export (Fuse meter)"** trace — the supplier's smart-meter export per day, read from the local Fuse cache only via `fuse_client.load_daily_export_kwh(fuseDataDir)` (no Fuse login during graphing; run `fusedata.py` first to refresh). The per-day interval-detail charts likewise overlay **"Export (Fuse meter, hourly avg)"**: `fuse_client.load_hourly_export_kwh(dir, date)` → `_fuse_hourly_series` (each hour's kWh × 1000 = average W, drawn as an `hv` step on the `'HH:MM'` category axis with a closing `23:55` point), threaded through `_interval_detail_figures(..., fuse_hourly_lookup)` and the three top/bottom wrappers. Omitted when the cache is empty; `fuseDataDir` (default `fuseenergydata`) is a graphs.py-specific key.
- `dailyseries.py` — `DailyRow` dataclass and `DailySeriesBuilder`: builds one `DailyRow` (spend, export income, savings, cumulative savings/ROI, energy flows, battery kWh) per date, using the same per-kWh formula as `EnergySummary.recalculate()` applied to a single day instead of a period total. `cumulative_investment` is held constant per run so a payback chart's crossover point reads as raw cash flow.
- `runCollectData.sh` / `runGraphs.sh` / `runFuseData.sh` — Linux/Debian launchers; prompt for credentials if not already set as env vars (password prompt is silent). Run from any directory.
- `runCollectData.bat` / `runGraphs.bat` / `runFuseData.bat` — Windows equivalents of the above.
- `energy_client.py` — `SunsynkEnergyClient(SunsynkClient)`: subclass that adds `get_energy_day()`, `get_energy_month()`, and `_get_cached()` (local file caching to `inverterData/day-YYYY-MM-DD.json` and `inverterData/month-YYYY-MM.json`; skips the API call if a cached file exists, and skips writing for the current day or month). The "do not cache" check uses `date != self._today[:len(date)]` — works for both day (`YYYY-MM-DD`) and month (`YYYY-MM`) keys. Accesses the parent's private HTTP method via its mangled name `_SunsynkClient__get` — noted in the class docstring.
- `fuse_client.py` — `FuseEnergyClient`: async (aiohttp) client for the Fuse Energy web app's tRPC endpoints (no public API; reverse-engineered from browser traffic). Auth: `POST /api/trpc/phoneSignIn {phone}` → SMS → `POST /api/trpc/verifyOtp {code}` sets a year-long `app-auth` cookie; `session_id`+`app-auth` are persisted to `{data_dir}/.session.json` (mode 0600) and validated via `getUnreadNotificationsCount` on `login()`. Any 401/403/tRPC `UNAUTHORIZED` raises `FuseAuthError` and `_trpc_get` re-signs-in once. Data comes from `premisesDisplayData` with `index` `{year}` (monthly bars), `{year,month}` (daily), `{year,month,day}` (24 hourly bars — the finest granularity seen in the web app's traffic; half-hourly not found); premises ID is scraped from `/app` (`RSC: 1`) unless `premisesFid` is configured. Files: `year-YYYY.json`, `month-YYYY-MM.json`, `day-YYYY-MM-DD.json`, `contracts-YYYY.json` (raw tRPC envelope). `load_daily_export_kwh(data_dir)` is a network-free reader for graphs.py: `{'YYYY-MM-DD': kWh}` from REALISED bars in `month-*.json`, falling back to summing `day-*.json` hourly bars for dates no month file covers (the current month). `load_hourly_export_kwh(data_dir, date_str)` returns `[(hour, kWh)]` from one cached day file (`[]` if absent). Cache rule (`is_final`): write only once the period has ended AND every bar is `REALISED` (smart-meter data lags), or unconditionally once it ended more than `FINAL_GRACE_DAYS` (14) ago.
- `fusedata.py` — CLI for the above; settings from the `fuse` object in `config.json` (`phone`, `premisesFid`, `startDate`, `stopDate`, `days`, `dataDir`) overridden by `key:value` args; `$FUSE_PHONE` beats config. `collect()` walks year views backwards from `stopDate` until an empty year, then months, then days (≤ today), and prints a monthly export kWh/£ summary plus API-call vs cache-hit counts.
- `indra_client.py` — `IndraClient`: async (aiohttp) client for api.indra.co.uk, reverse-engineered from the Indra Android app (a .NET MAUI app with an NSwag-generated client). Auth: `GET api/user/check/{email}/{deviceKey}/2` (2 = Android; we use our own random `deviceKey` so the phone app's session is untouched) emails a sign-in link and returns a check hash; the link (`…/mobile/verify/{env}/{email}/{mobileHash}/{hash}`) is either pasted, in which case we call `api/user/verify/{email}/{mobileHash}/{hash}`, or opened on the phone, in which case we just poll; then `GET api/user/token/{email}/{deviceKey}/{checkHash}/2` (400 "User Not Activated" until then) returns a 30-day JWT used as `Bearer`. `login()` reuses the saved token, renewing it via `api/authorize/refresh` when under `REFRESH_WITHIN_DAYS` remain (expiry read from the JWT payload); a 401/403 on a data call triggers one re-sign-in. Requests time out after `REQUEST_TIMEOUT` and are retried `NETWORK_RETRIES` times. Data: `api/reports/monthly/{y}/{m}` (one `dailyReports` entry per day, energy split Off-Peak/Standard by when it was drawn, so overnight sessions span two days) → `month-YYYY-MM.json`; `api/reports/transactions/index/{y}/{m}` → `sessions-YYYY-MM.json`; `api/reports/transactions/{id}` (UTC start/end, totals, split) → `session-{id}.json`; `…/{id}/telemetry` (per-minute `powerKw`, `tariffRateType`) → `telemetry-{id}.json`. Cache rule: a file is always (re)written with the latest copy, but only *re-used* without refetching once final (month ended more than `FINAL_GRACE_DAYS` (3) ago; session has an `end`). Early months (Apr–May 2025) have daily totals but an empty session index. `load_daily_charge_kwh(data_dir)` is the network-free reader: `{'YYYY-MM-DD': {off_peak, standard, total, cost}}` from the month files. `api/devices` returns the home address, so nothing from `indraData/` may ever be committed.
- `indradata.py` — CLI for the above; settings from the `indra` object in `config.json` < `config.local.json` (`email`, `startDate`, `stopDate`, `sessions`, `telemetry`, `dataDir`) < `key:value` args; `$INDRA_EMAIL` beats config. `collect()` walks months back from `stopDate` to `startDate`, or until `EMPTY_MONTHS_STOP` (3) empty months in a row, fetching each monthly report and optionally every session plus its telemetry, and prints a monthly kWh (off-peak/standard), £ and session-count summary plus API-call vs cache-hit counts.
- `evcharging.py` — `load_ev_profiles(data_dir)` → `{'YYYY-MM-DD': {'HH:MM': W}}` (Europe/London local date and 5-minute slot, average W) from the cached Indra sessions. Uses per-minute telemetry where cached (Indra keeps only ~3 months; each sample is held until the next one, capped at 5 min). Older sessions are reconstructed (`synthesise_wh`) at the median telemetry charger power (~7.45 kW): Off-Peak kWh from the start of the session's scheduled `events` window, Standard kWh from plug-in outside it, and any overflow spread over the session. Checked against telemetry, 96% of energy lands in the right hour. Indra's own *daily* reports bucket by UTC day, so they don't line up exactly with local-day sums.
- `exportcheck.py` — network-free CLI: corrected inverter export vs Fuse meter per day, totals before/after `splitDate`, and a least-squares gain/standby refit vs the `exportCorrection` config.
- `pvcheck.py` — soiling/degradation check. Fetches hourly GHI/DNI/DHI/temperature from the Open-Meteo archive API (`timezone=GMT`; each value is the mean of the PRECEDING hour) and caches a file per month in `weatherData/openmeteo-{lat}_{lon}-YYYY-MM.json`, written only once the month ended more than `FINAL_AFTER_DAYS` ago. Sunsynk PV samples (local Europe/London time, gap-filled) are binned to UTC hour-ending keys (`load_pv_hours`). Hours with any sample ≥ 97% of the all-time max are dropped as clipped. Plane-of-array irradiance comes from its own NOAA sun position (evaluated at mid-hour) plus an isotropic-sky model. Expected Wh = `panelWatts` × POA/1000 × a temperature derate (−0.35%/°C, cell = air + 0.03·POA), and PR = actual/expected over hours with POA ≥ 100 W/m², with a "sunny" (DNI ≥ 400) subset. `fit_orientation` grid-searches tilt/azimuth (degrees from south, +west) on the first 120 days if `pvCheck.tiltDeg`/`azimuthDeg` are unset; the fitted values are 40°/−38°. YoY compares only dates present in both years (`_year_back`). Settings merge `config.json` `pvCheck` < `config.local.json` `pvCheck` (git-ignored, holds lat/lon because the repo is public) < CLI. Weekly PR is noisy (±10%, from the ~10 km reanalysis grid), so only monthly or longer aggregates are meaningful.
- `tariff_sources.py` — fetches current import tariffs as 48 local half-hour p/kWh (`slot_rates`) plus standing charge, cached per day in `tariffData/{YYYY-MM-DD}/` (`Fetcher`: aiohttp, browser User-Agent, file cache, concurrency cap). Sources: **Kraken REST APIs** (no auth) — Octopus `api.octopus.energy` (also lists Co-op and London Power), E.ON Next `api.eonnext-kraken.energy` (also Sainsbury's, and `SMART_NEW_CO` = Next Flex), EDF `api.edfgb-kraken.energy`: `/v1/products/` → newest version per family (`family_key` strips `-YY-MM-DD` / `_Vn` / `_HH`) minus `exclude` (export, prepay, heat-pump, hardware-tied, employee …) → product detail's `single_register_electricity_tariffs['_{region}'].direct_debit_monthly` → its `standard-unit-rates` timeline (UTC) over the last `rateDays` days averaged into local half-hours (`rates_to_slots`; BST-safe), which yields TOU windows and Agile/FreePhase Dynamic averages exactly. Intelligent Octopus Go has no single-register tariff: it's in `four_rate_ev_electricity_tariffs` (day/night + EV-device rates, no times), so its window is parsed from the product description (`_window_from_text`) and `ev_rate` = EV-device off-peak rate. **energyplus.co.uk** (British Gas, OVO, Scottish Power have no API): `/suppliers/{slug}/tariffs` index → each tariff page's "Electricity, Monthly Direct Debit, standard-rate|Economy 7: regional prices" table row for the region (`REGION_NAMES`); E7-only (EV) tariffs need a window from `windows` (name regex → `HH:MM-HH:MM`; BG EV Power / SP EV Saver 00:00-05:00). **Ofgem price cap**: the Direct Debit single-rate table is an everviz widget (`app.everviz.com/inject/{id}/`, a JSON row array; newest period = last columns). **OVO Charge Anytime** add-on rate scraped from OVO's page and applied (smart EV) to the cheapest OVO tariff and the cap. **Export tariffs** come from the same Kraken hosts (`kraken_tariffs(..., direction='EXPORT')`: products with `direction == 'EXPORT'`, minus `exportExclude` (Zero Bills, Power Pack, Flux, and E.ON Next Export Premium, which needs an E.ON-installed system)); `exportFlatImportOnly` marks export tariffs barred with time-of-use imports (E.ON Next Export Exclusive: "excluding time of use tariffs i.e. Next Drive"), which `best_pairs` only pairs with single-rate imports → `_as_export`: standing 0, `requires` = the supplier whose import tariff it's assumed to need (`exportRequires` regex → supplier, e.g. Outgoing/Agile Outgoing/Prime → Octopus, E.ON `NEXT_EXPORT*` → E.ON Next; Octopus/Co-op export-only SEG are open), note = first sentence of the product description. Every tariff dict has `direction` (`IMPORT`/`EXPORT`). `manualTariffs` / `manualExportTariffs` (`rate`, `requires`) config entries are also supported. Settings (`DEFAULTS`): `tariffCompare` in config.json < config.local.json < CLI.
- `tariffcompare.py` — CLI: runs `_iter_energy_days` (first energyPrices file, baseline PV, EV on) feeding `EnergyDay.import_slots()` into `projection.SlotProjection`; `annual_profile` = seasonal house import per half-hour + EV year (projected annual import from `get_derived()` minus house, i.e. the rebased `evBasisFrom` EV year) spread over the EV half-hour shape since `evBasisFrom`. `price_tariff` splits each import tariff into `house_cost`, `ev_now`, `ev_retimed`, `ev_p_per_kwh` and `standing_year`, and gives "as now" (each half-hour at the tariff's rate) and "EV re-timed" (EV energy in the current off-peak window → tariff's cheapest rate; smart-EV tariffs: all EV import at `ev_rate`), both + 365 × standing; export not included. The current tariff (newest period of the energyPrices file, `current_tariff`) is ranked alongside. Export: `SlotProjection.annual_export()` (fed by `EnergyDay.export_slots()`; checked against `SeasonalProjection.annual_kwh('export')`) priced per half-hour by `compare_exports` against the export tariffs and `current_export` (the energyPrices export rate); `best_pairs` lists the cheapest import − export pairs, an export tariff with `requires` only going with that supplier's import, and the current import only with the current export (a new import can keep the current export, e.g. Fuse). Prints IMPORT TARIFFS (house/EV/standing split), PROJECTED EXPORT (annual, average month, time-of-day share), EXPORT TARIFFS, BEST IMPORT + EXPORT PAIRS and PAIR DETAIL (`pair_breakdown`: rates, house peak/off-peak kWh/£/p (off-peak = the import tariff's cheapest-rate half-hours), EV, standing, export, net, for the top 6 pairs + current), and writes both directions to `results/_{ts}-tariffs-{region}.csv`.
- `energymonth.py` — `EnergyMonth`: parses monthly daily kWh totals from the plant energy month endpoint (Load, PV, Export, Import labels).
- `energyday.py` — `IntervalSummary` and `EnergyDay` (`import_slots()` → `(total, ev)` import Wh and `export_slots()` → corrected export Wh per local half-hour, same per-sample rules as the Grid summary): parse the 5-minute interval timeseries from the plant energy day endpoint. `IntervalSummary` accumulates peak/offpeak Wh totals for one label (PV, Grid, Load); named `IntervalSummary` to avoid a name clash with `energysummary.py`'s `EnergySummary`. `EnergyDay.__init__` first runs `_fill_gaps()` on the PV/Grid/Load records (new lists, raw dict untouched): the API drops ~7 of 288 samples a day (10–20 min gaps) and every record is treated as 5 min of energy (`value/12`), so gaps ≤ 30 min are forward-filled to a regular 5-minute grid (longer gaps — e.g. the hourly test fixtures — are left alone). Negative Grid samples (export) go through `ExportCorrection.split(wh) -> (export_wh, standby_wh)`: `export × gain`, minus a `standby_w` load sitting between the inverter CT and the meter (EV charger standby) — only the standby part is credited as self-consumed house load (subtracted from import); the `(1-gain)` part is just lost export. Used identically by `IntervalSummary` and `run_battery()`. `ev_watts` (`{'HH:MM': W}`, one day of `evcharging.load_ev_profiles`) models the EV charger, which sits beyond the inverter CT. It is added to Load and to the net Grid (adding records for slots Sunsynk didn't sample), so it absorbs CT-measured export first (`get_calc_ev_from_pv()`) and the rest becomes import. `self.ev` is an `IntervalSummary` of the EV draw (`get_calc_ev(qtype)`). The battery replay keeps the CT-side Grid (`_battery_grid`), because a battery behind the CT couldn't feed the car. `EnergySummary` keeps `total_ev_*`, prices EV energy as `ev_import_cost`/`ev_lost_export`, and excludes EV off-peak kWh from `off_peak_excess` (car charging isn't house load shifted to off-peak). `EnergyPrices.print_ev()` prints the EV CHARGING section, and `get_derived()` adds `annual_ev_kwh`/`annual_ev_cost` (projection keys `ev_peak`/`ev_off_peak`/`ev_from_pv`). `evBasisFrom` (config.json: `2026-05-01`, when a second EV arrived; CLI `evBasisFrom:`, where `''` means seasonal) → `EnergyPrices(ev_basis_from=)` puts EV kWh into separate before/after projections. `projection.rebased_annual_ev` then counts calendar months seen since the basis as measured, and scales months seen only before it by the after/before ratio over shared months (2.43 on 2026-10 data). The peak/off-peak/solar split follows the after period. `annual_import_*` swaps the seasonal EV share for that rebased year, and `ev_basis_ratio`/`ev_basis_months` are reported. In `collectdata.py`, `evCharging` (default ON) / `evDataDir` (default `indraData`) → `_load_ev_profiles(settings)`, passed as `_iter_energy_days(..., ev_profiles)` (part of the energyday cache key). graphs.py does the same. Inverter-reported (`supplied_*`) figures never include EV. The Android app mirrors all of this (see below). Defaults (`gain=1.0`, `standby_w=27.6` = the old hardcoded 2.3 Wh/5 min) reproduce the original rule. The Android app mirrors this: `fillGaps()`/`ExportCorrection` in `android/.../analysis/EnergyDay.kt`, `ExportCorrectionConfig` (parsed from the same `exportCorrection` block, editable in the Config screen) in `AppSettings.kt`; installs whose saved config predates the block adopt it from the bundled `assets/config.json`. Parity with the Python numbers is checked by JVM unit tests (`./gradlew testDebugUnitTest`).
- `pricedata.py` — `PriceData` dataclass: energy tariff rates (off-peak/peak/export rates, standing charge, off-peak window). Hardcoded defaults, overridden per-period by `EnergyPrices.check_date()`. `off_peak_baseline_kwh` is the configurable reference (kWh/day for a 7-hour window) used to estimate baseline off-peak usage; `off_peak_average` is computed from it by `EnergySummary` — do not set directly.
- `virtualbattery.py` — `VirtualBattery`: simulates battery charge/discharge over historical 5-minute intervals, tracking kWh drawn, charged, and PV-charged to compute potential savings. Named `VirtualBattery` to distinguish it from the upstream `Battery` model (realtime API response). `grid_charge=False` disables grid top-up at off-peak (models PV-only charging).
- **PV boost ("plug-in solar")**: `EnergyDay.__init__` takes `pv_extra_ratio` (= `addWatts / existingPvWatts`) and `pv_extra_clip_w` (microinverter AC clip, or `None`). When `pv_extra_ratio > 0` it builds fresh PV/Grid record lists — `extra = min(pv_extra_ratio × PV[t], clip)`, added to PV and subtracted from Grid — without mutating the shared raw dict, and accumulates `pv_clip_loss` (Wh discarded by the clip, via `get_pv_clip_loss()`). `EnergySummary` carries `total_pv_clip_loss`. In `collectdata.py`, `_normalize_pv_boosts` turns the `pvBoost` config (single object or list of `{label, addWatts, cost, inverterClipW}`) into scenarios with a zero-add baseline first; `main()` loops boosts as the outermost dimension (baseline drives the standard report), `_energyday_cache` is keyed by ratio+clip, and `_pv_boost_metrics` / `_print_pv_boost_comparison` render the `PV BOOST COMPARISON` table (deltas vs baseline over a seasonally weighted year at the latest rates, from each scenario's `EnergyPrices.projection`).
- `energysummary.py` — `QueryType` enum, `EnergySummary`, and `EnergySummaryAggregator`:
  - `EnergySummary` — accumulates per-day financial data for a single tariff period; `new_month()` compounds interest on cumulative savings. Computes `off_peak_average` from `price_data.off_peak_baseline_kwh` scaled to the actual window length.
  - `EnergySummaryAggregator` — holds one `EnergySummary` per tariff period and computes cross-period grand totals.
- `energyprices.py` — `EnergyPrices`: top-level orchestrator; reads one or more `_EnergyPrices*.json` files (supports multi-file tariff comparison), calls `check_date()` to switch tariff periods, and exposes `print_*` methods for the final report. Constructor params: `off_peak_baseline_kwh`, `off_peak_shift_enabled` (include off-peak load-shifting in savings), `battery_enabled` (show/include virtual battery section), `battery_price` (£ cost of battery; triggers payback-period display in `print_battery()` and comparison table). `add_data()` also records each day's kWh (plus the simulation battery's counter deltas, reset whenever `check_date()` swaps in a new battery) into `self.projection`; `get_derived()`'s forward-looking figures (`annualised_solar`, `solar_payback_years`, `solar_payback_remaining_years`, `annualised_battery`, battery `payback_years`) come from it, not ×365/days, as does the `PROJECTED YEARLY IMPORT` block (`print_projected_import()`, called from `print_averages()`: peak/off-peak kWh and £ plus a year's standing charge, keys `annual_import_*` / `annual_standing_charge`). Actual-to-date figures (savings, ROI %, cumulative) still use the historical rates.
- `projection.py` — `SeasonalProjection`, `SlotProjection` (per-month, per-half-hour house/EV import and export for tariffcompare.py) and `latest_rates(prices)`. kWh are kept per calendar month; `annual_kwh()` averages each calendar month over every year seen and weights it by month length (so the season covered, or a month recorded twice, can't skew the year), falling back to ×365/days — flagged provisional — until all 12 months exist. `annual_money(rates)` prices them at one rate set: always the newest started tariff period (`latest_rates`), so a cut SEG or import rate flows straight into payback. Historical peak/off-peak kWh splits keep the window in force on each day. Android mirror: `analysis/Projection.kt`.

### Energy price data files (`inverterData/_EnergyPrices*.json`)

JSON files defining tariff periods with fields: `datefrom`, `dateto`, `offpeakRate`, `offpeakStart`, `offpeakStop`, `peakRate`, `exportRate`, `standingCharge`, `InterestRate`. (`CompareRate` and `CompareStandingCharge` are silently ignored if present in older files.)

`energyPrices` in `config.json` can be a single filename string or a list of filenames for side-by-side tariff comparison.

`virtualBattery` in `config.json` can be a single config object (current default) or a list of config objects for side-by-side battery comparison. Each object in the list can have an optional `label` field and only needs to specify fields that differ from the defaults. CLI battery overrides (e.g. `batterySize:N`) apply to all configs in the list. In multi-battery mode, solar/tariff output is printed once (first config); battery sections are printed per config; a `BATTERY COMPARISON` table follows. `_make_battery(vb, price_data)` takes the battery config dict directly.

`exportCorrection` in `config.json` — `{gain, chargerStandbyW, chargerOff: [[from, to], ...]}` (CLI `exportGain:N`, `chargerStandbyW:N`; defaults `1.0` / `27.6` / `[]`) — calibrates inverter export to the supplier's smart meter. `_export_correction_for(date, cfg)` resolves it per date (standby 0 inside any inclusive `chargerOff` range) and `_iter_energy_days(..., export_correction_cfg)` passes it into each `EnergyDay` (it is part of the `energyday_cache` key). Current values (gain 0.953, 11 W, charger off 2026-08-06..25) were fitted against Fuse meter data 7 Aug–30 Sep 2026: with the charger off the meter read 0.952 × inverter export — a proportional CT error, not a fixed inverter draw (fixed-draw fits were clearly worse).

`pvBoost` in `config.json` (with top-level `existingPvWatts`, default 3115) is an optional single object or list of `{label, addWatts, cost, inverterClipW}` describing added "plug-in solar" panels. `_normalize_pv_boosts` always puts a zero-add baseline first; when any option adds watts, a `PV BOOST COMPARISON` table is printed (deltas vs baseline per seasonally weighted year at the latest rates, using the first battery config and first tariff file). Absent `pvBoost` ⇒ single baseline ⇒ output identical to before.

## Tests

Tests use `pytest-asyncio` and `pytest-aiohttp`. The `MockApiServer` in `tests/mock_api_server.py` spins up a local aiohttp server that generates a real RSA key pair, serves it via `/anonymous/publicKey`, and verifies the encrypted password on login — matching the real API's auth flow. It also serves `/api/v1/plant/energy/{plant_id}/month` and `/api/v1/plant/energy/{plant_id}/day` for energy endpoint tests. Tests are all async and use `aiohttp_client` + `event_loop` fixtures.
